# 高德：持续进化的个人位置智能体

整理日期：2026-10-26  
材料：[课程 850](https://open.oceanbase.com/course/850) · [高德官方解析视频](https://www.oceanbase.com/video/9002448)，约 17 分 22 秒

## 1. 这道题主要做什么

方向是构建能感知位置、形成记忆、学习偏好并持续进化的个人位置智能体。课程用旅行规划作为主要场景：用户说出目标、时间和偏好，系统结合真实地理数据，形成可以执行和调整的计划。

例如，用户提出“一天游览几个地方、步行少一些、晚上回到酒店”，系统应完成地点选择、访问顺序、交通与时间安排。用户修改条件后，系统能够重新规划，并在后续任务中恰当地使用已确认的偏好。这个例子是实现建议，不是官方指定测试用例。

## 2. 课程强调的三个问题

| 问题 | 为什么会成为工作重点 |
|---|---|
| 空间计算 | 多目的地、可选地点、停留时间和多交通方式，使规划比单一起终点导航复杂。 |
| 数据与决策 | POI、路网、交通、时段、用户偏好等信息来源分散，需要获取、清洗和组合。 |
| 产品交互 | 用户需要比较、理解和调整方案；过少的信息难以决策，过多的信息又造成负担。 |

高德 API 提供地点、路径和空间表达等基础能力。选手需要把这些原子能力组织成智能体可调用的工具，并建立从需求到决策的完整流程。

**材料边界**：课程未给出完整评分表和正式交付清单。后半段的门店运营、商业选址和热力分析案例是在介绍平台能力，不能全部算作必做任务。

## 3. 建议的最小实现范围

先选择一个城市、一个出行时段和一种主交通方式，覆盖少量候选地点；在正式规则允许的范围内，逐步增加复杂度。

建议跑通以下流程：

```text
用户需求与已确认偏好
  → 提取时间、预算、交通和地点约束
  → 获取并核验候选 POI
  → 调用路线工具、计算可行方案
  → 地图展示与方案比较
  → 用户修改或确认
  → 更新适用的记忆和后续计划
```

第一版至少应展示一次真实的条件变更：更换一个目的地、缩短可用时间，或调整交通方式。重新规划后仍需检查全部有效约束。

## 4. 模块与数据设计建议

- **需求理解**：把自然语言转换为明确条件，区分用户必须满足的要求与可调整偏好。
- **空间工具**：为地点搜索、地理编码、路线等能力定义结构化输入、输出和失败状态。
- **规划与校验**：组合候选方案，校验时间、访问顺序、交通和已知开放条件，标明无法核实的信息。
- **数据与记忆**：保存来源、获取时间和适用范围；区分长期偏好与本次任务限制。
- **交互展示**：地图与时间线相互对应，支持查看依据、替换地点和重新规划。

模型适合解释用户意图、提出候选和组织步骤；距离、通行与时长等数值应由真实工具结果和明确计算支撑。工具失败时，应呈现失败或请求调整，不能补造一个成功结果。

这里是功能划分建议，不代表必须部署成多个服务。课程也未完整确认 seekdb、PowerContext 的具体强制使用方式，需以后续题包为准。

## 5. 如何做记忆与持续进化

“记住用户”应有可验证的行为。建议记录偏好值、来源、确认时间和作用范围。例如，“本次陪老人出游，减少步行”可以只属于本轮任务，不应直接变成用户永久偏好。

至少验证三种情况：

1. 用户明确表达的偏好能影响下一次候选选择。
2. 用户修改或撤回偏好后，新方案使用最新状态。
3. 临时要求不会无条件污染长期画像。

这些属于建议验证设计，并非课程公布的官方评分条目。

## 6. 怎样证明方案可用

| 验证方向 | 建议证据 |
|---|---|
| 数据真实 | 展示地点标识、数据来源、获取时间和工具返回。 |
| 约束可行 | 逐项检查时间、交通和用户硬性要求，并解释不满足之处。 |
| 修改有效 | 改变条件后重规划，其他有效要求继续保留。 |
| 记忆有效 | 用连续任务对比有无已确认偏好时的选择。 |
| 产品可理解 | 用户能够查看路线、比较候选、修改决定，而非只收到一大段文字。 |
| 系统稳定 | 处理查无地点、接口超时、限额和结果不完整。 |

性能指标可记录规划耗时和接口调用次数，但应先保证数据可靠与方案可执行。不要为了展示丰富功能，把不可获得的热力或经营数据当成默认依赖。

## 7. 建议准备的交付物与待确认问题

在正式清单发布前，可准备：可运行应用、源码与部署说明、空间工具列表、示例任务、路线与约束验证记录、记忆更新案例和技术方案。

优先确认正式题包是否限定具体场景、必须使用的数据库/记忆组件、数据来源和接口权益，以及评测任务和提交格式。先核实数据和接口可用性，再承诺更复杂的功能范围。
