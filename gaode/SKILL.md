# 周边去哪儿

## 1. 名称、用途和适用场景

- 名称：around-where-to-go（周边去哪儿）。
- 用途：用户用一句话找附近地点，并知道怎么步行到达。助手先查真实地点，再查从同一起点到每个候选地点的步行路线，最后给出简洁、可核对的推荐。
- 适用场景：输入包含城市、起点和自然语言需求。例如：“我在杭州某地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。”
- 适用地点类型：咖啡馆、餐厅、公园，以及用户明确说出的其他附近地点类型。
- 不适用：设备定位或 IP 定位；把多个地点串成一条多站行程；驾车、公交、骑行或打车作为默认出行方式；长期记忆、多轮偏好、PowerMem 或 seekdb。评测是单轮任务，做完“提出需求 → 查询高德 → 返回推荐”即可。
- 运行环境：评测平台提供模型、Agent 和高德 MCP 配置。只调用已经配置好的工具。不要创建或修改 MCP 配置，不要读取、猜测、填写或输出 API Key，不要把密钥写进回答。

各地点都是从同一个起点出发的独立备选，不是前后衔接的行程。回答中的地点名称、地址、坐标和步行距离、时间必须来自本次工具结果，并与工具返回一致。

## 2. 输入怎么理解

评测会给明确起点坐标。不要做设备定位，不要调用 `maps_ip_location` 猜测用户位置，也不要要求 GPS。

从用户消息中读取：

1. 城市：用于限制关键词搜索和核对地点所在城市。不要因为“杭州”和“杭州市”这种写法差异排除地点。
2. 起点：优先使用消息里给出的坐标，格式为“经度,纬度”。去掉空格；中文逗号改成英文逗号。不要擅自对调经纬度。同时给出地名和坐标时，以坐标为准。只有完全没有坐标、只给了起点地名时，才可以用 `maps_geo` 按该地名和城市解析坐标；这不是设备定位。
3. 地点类型：使用用户原话，例如咖啡馆、餐厅、公园。用户没指定类型时，不要默认成咖啡馆。
4. 步行时间上限：识别“不超过 N 分钟”“N 分钟内”“N 分钟以内”。比较时使用路线返回的秒数，`duration <= N * 60`。不要四舍五入后比较，避免 15 分 01 秒被算成 15 分钟内。
5. 推荐数量：识别“最多 N 家”“推荐 N 家”。实际返回数量是 `min(N, 3)`。用户没说数量时按 3。用户要多于 3 家时仍最多返回 3，并说明上限。
6. 排序偏好：用户说“优先更近”“优先近一点”“近一点”时，符合条件的地点必须按步行时间从短到长排列；时间相同再按步行距离从短到长。没说排序时，也按步行时间从短到长，并写明这是默认顺序。

没有步行时间上限时，不要自己补一个上限。有上限时，超过上限的地点不能算符合条件，不能放进推荐列表。

## 3. 使用哪些高德工具

工具名以高德 MCP Server 为准。地点搜索用周边搜索；步行到达信息用步行路径规划。官方服务里的对应工具名是 `maps_around_search` 和 `maps_direction_walking`。坐标不在搜索结果里时，用 `maps_search_detail` 补齐。不要改用其他开源实现里的别名。

坐标格式一律是“经度,纬度”。

### 3.1 周边搜索 `maps_around_search`

按起点和地点类型查询附近地点。参数：

- `location`：起点坐标，必填。
- `keywords`：地点类型关键词。咖啡馆用“咖啡”，餐厅用“餐厅”，公园用“公园”；其他类型用用户原话中的类型词。
- `radius`：只用于召回候选的搜索半径，单位米，传字符串，不超过 50000。有步行时间上限 T 分钟时，先用 `min(5000, max(1500, T * 100))`。没有上限时先用 `2000`。

返回的 `pois` 里使用本次实际给出的 `id`、`name`、`address`、`typecode`。不要假设一定带有坐标。

### 3.2 关键词搜索 `maps_text_search`

只在周边搜索成功但 `pois` 为空时，作为一次补充检索。参数：

- `keywords`：必填，与周边搜索相同。
- `city`：用户给出的城市。
- `types`：仅当工具 schema 明确要求或用户给了可对应的类型词时才传。

关键词搜索不是附近搜索。它的结果仍要拿到坐标并做步行路线筛选，不能直接推荐。周边搜索报错时，不要改用关键词搜索假装成功。

### 3.3 详情搜索 `maps_search_detail`

参数只有 `id`，即搜索结果中的 POI ID。用它取得 `location`、`address`、`type`、`city`、`business_area`。只有这些字段真实出现且非空时才能引用。`location` 是步行路线的终点坐标。

### 3.4 步行路线 `maps_direction_walking`

对每个还可能入选的候选单独调用。参数：

- `origin`：同一个起点坐标。
- `destination`：该地点的 `location`。

从返回结果读取步行方案的 `distance` 和 `duration`。常见位置是 `route.paths`；若嵌套不同，以本次返回中的 `paths[].distance` 和 `paths[].duration` 为准。`distance` 单位是米，`duration` 单位是秒。有多条 `paths` 时取 `duration` 最短的一条，并在理由里说明。全程距离和时间用这条 path 的值，不要把某个 step 的距离当成全程，也不要把多个地点的时间相加。

步行时间必须来自这次步行路线查询。步行时间不能用直线距离代替。禁止用直线距离代替步行时间或步行距离。

## 4. 查询、筛选和回答步骤

在工具返回之前，不要先写出推荐名单。调用顺序如下。

1. 解析城市、起点坐标、地点类型、步行时间上限、推荐数量和排序偏好。数量最终不超过 3。
2. 用 `maps_around_search` 查询地点。不要用 IP 或设备位置填充 `location`。
3. 同一 `id` 只保留一条。按名称和类型核对地点类型：类型文本、`typecode` 或名称应能对应用户要求。明确是其他类型的地点排除。用户没指定类型时，保留周边结果，并说明这不是某一固定品类。
4. 候选已有“经度,纬度”就使用该坐标。没有坐标但有 `id` 时，调用 `maps_search_detail`。没有 `id` 也没有坐标的地点不能推荐，不能编造坐标。
5. 详情里的城市与用户城市明显冲突时排除该地点并说明。只是行政区名称写法不同则保留。
6. 对保留下来的候选调用 `maps_direction_walking`。同一页搜索结果里、类型符合的候选都要查路线后再排序；不要只凭搜索返回的先后，就把未查路线的地点排进“更近”。
7. 路线失败、没有 `paths`，或 `distance`、`duration` 不能解析为非负数字的地点，不能算符合条件。
8. 有步行时间上限时，只保留 `duration <= N * 60` 的地点。超时地点不能算符合条件。
9. 按第 2 节的排序规则排列。用户说优先更近时，列表顺序必须和步行时间一致。
10. 取排序后的前 `min(用户要求数量, 3)` 条。不足就少返回，并说明原因。
11. 按第 5 节输出。每个推荐地点的名称、地址、米数和秒数都要能在本次工具结果中找到。

搜索半径不是步行时间。第一次筛选后符合条件的数量仍少于需要返回的数量时，可以把半径扩大一倍后再查一次，扩大后不超过 5000 米；然后重复坐标补齐、步行路线和秒数筛选。扩大后仍不足，就返回已符合条件的地点，不要为了凑满 3 个继续放宽到整个城市，也不要把超时地点补进来。

同一工具调用如果返回传输错误或服务错误，可以用相同参数重试一次。再次失败就停止该步骤并如实说明。不要连续换参数直到编出结果。

## 5. 回答格式

用中文列表或表格。推荐表只放符合条件的地点，最多 3 行。列至少包括：地点名称、地址、预计步行距离、预计步行时间、推荐理由。

| 序号 | 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- | --- |
| 1 | 工具返回的名称 | 工具返回的地址 | 路线 distance 的米数 | 由 duration 秒换算，并保留总秒数 | 一句有数据依据的理由 |

填写规则：

- 名称照抄工具返回，不要改成另一个店名。
- 地址优先用详情中的非空地址，否则用搜索结果中的非空地址。两边都没有时写“地址未在查询结果中给出”，不要编造街道。
- 预计步行距离写路线的米数，例如“820 米”。超过 1000 米时可以同时写公里，但米数必须与工具返回一致。
- 预计步行时间同时写换算结果和总秒数，例如“13 分 20 秒（800 秒）”。秒数必须等于所选步行方案的 `duration`。
- 推荐理由只写一句，并且能指出数据依据：地点类型如何匹配、步行多少米、步行多少秒，以及它在本次符合条件的结果中是步行时间第几短。用户要求优先更近时，第一名的理由要写明它的步行时间最短。
- 路线如果返回了首段 `steps[0].instruction`，可以在该地点下另起一行，原样引用为“步行提示”。没有该字段就不要写导航句子。

表格后按需附上短说明，没有就省略对应项，但第 6 节的失败、不足和未核实不能省略：

- 排序依据：写明按步行路线耗时从短到长，或用户指定且工具数据能够支持的顺序。
- 未纳入：超时或类型不符的地点只写在这里，附上真实步行秒数或排除原因，不放进推荐表。
- 数量不足：写明查到了多少个符合条件的地点，以及为什么少于用户要的数量。
- 未核实信息。

没有符合条件的地点时，不要输出空表，也不要保留示例里的占位文字。直接说明没有可推荐结果、原因和建议。

## 6. 结果不足、信息缺失和失败处理

### 6.1 结果不足或没有结果

符合条件的地点少于要求数量时，不够就少返回，并说明原因，例如搜索页内只有 1 个地点的步行时间在上限内。一个都没有时，明确写查询范围内没有符合条件的地点。可以建议放宽步行时间、更换地点类型或扩大范围。不要编造地点和路线来凑数。数量为零本身不是错误；把“没有结果”说清楚就是正确处理。

### 6.2 未核实

安静程度、排队情况、营业状态，以及评分、人均和价格，只有本次工具结果里存在对应的非空字段时才能引用，并写明字段来自详情。没有这些字段时，必须写“未核实”，不能根据店名、常识或路线长短推断。

营业时间文本如果真的出现，只能作为原文引用；不要据此判断现在是否在营业。当前营业状态没有明确字段时仍写未核实。安静程度和排队情况在普通地点搜索与步行路线结果中通常没有依据，默认写未核实。

### 6.3 查询失败

按实际失败步骤说明，不要把失败写成成功：

- 周边搜索失败：说明地点搜索失败，转述工具错误信息。不要改用想象中的附近店铺。
- 详情失败：该地点没有可靠坐标，不能进入推荐。所有候选都因此失败时，说明无法取得坐标，所以不能查询步行路线。
- 步行路线失败或没有路径：该地点不能算符合条件。全部候选的路线都失败时，说明步行路线查询失败，因此没有可推荐结果。
- 服务异常：说明高德工具服务异常或返回无法解析。不要编造地点、地址、距离和时间。

失败回答里仍然把缺少依据的安静程度、排队情况和营业状态标为未核实。可以建议稍后重试或放宽条件。

## 7. 禁止事项

- 禁止用直线距离代替步行时间或步行距离。不要调用 `maps_distance` 充当步行路线，无论 `type` 是 0（直线）、1（驾车）还是 3（步行测距）。不要用搜索半径、POI 自带距离、球面距离或自行计算的大圆距离填写“预计步行距离/时间”。
- 禁止在路线查询失败后，用步行速度乘以直线距离估算时间。
- 禁止编造工具没有返回的地点、地址、坐标、距离、时间和导航指令。
- 禁止把超时地点放进符合条件的推荐表。说明“未纳入”时也不能把它们叫作符合条件。
- 禁止返回超过 3 个推荐地点。
- 禁止把多个地点串成多站行程，或把各地点的步行时间加总。
- 禁止做设备定位，禁止用 IP 定位代替评测给出的起点坐标。
- 禁止在 Skill、参数或回答中写入 API Key。密钥只存在于评测平台的高德配置中。

## 8. 评测场景对应动作

- 普通推荐：按地点类型搜索，核对类型，查步行路线后最多返回 3 个真实地点。
- 时间限制：只把步行路线秒数落在上限内的地点算作符合条件；超时地点不进入推荐表。
- 偏好排序：用户说优先更近时，推荐顺序和推荐理由都与步行时间一致，时间短的在前。
- 结果不足或查询异常：少返回或不返回，写明没有足够结果或服务异常；不编造地点和路线，缺少依据的信息写未核实。
