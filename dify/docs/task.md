# Dify：工作流、Agent 与知识库应用工程

整理日期：2026-10-26  
材料：[课程 850](https://open.oceanbase.com/course/850) · [Dify 官方解析视频](https://www.oceanbase.com/video/9002457)，约 19 分 43 秒

## 1. 目前能确认的题目方向

这段课程介绍如何用 Dify 把模型、知识、工具和业务流程组织为持续运行的 AI 应用。准备重点包括工作流编排、知识库处理、检索优化、Agent 工具使用以及部署和运行观察。

**需要明确的边界**：该视频主要是平台教学，没有逐条公布完整赛题目标、验收标准和交付清单。因此，本文件中的产品方案和开发步骤是备赛建议，不能替代正式题面。

目前不宜直接认定某种聊天助手、某个业务场景，或某组节点就是官方指定作品。

## 2. 课程覆盖的主要能力

| 能力 | 在应用中解决什么问题 |
|---|---|
| Workflow / Chatflow | 将输入、处理、判断、调用和输出组织成有状态的流程。 |
| Agent | 处理任务路径不能完全预先确定的步骤，调用工具完成任务。 |
| 知识库 | 将文档导入、切分、向量化，提供检索和上下文。 |
| 检索优化 | 组合语义与关键词检索，并通过重排改善候选次序。 |
| 插件与外部工具 | 把模型连接到真实系统和业务动作。 |
| 运行观察 | 查看步骤、耗时、错误与调用成本，定位质量和稳定性问题。 |
| 部署 | 配置应用、数据服务、环境参数及运行依赖。 |

视频强调 Workflow 与 Agent 的配合：可以由确定的流程控制任务阶段，将不确定的子任务交给 Agent。使用 Agent 并不意味着每一步都交由模型自由决定。

## 3. 建议准备的最小作品

在正式场景未确定前，先做一个可以替换业务知识和工具的最小闭环。例如，“资料查询并形成有依据的处理建议”：

```text
用户请求 → 输入检查 → 知识检索 → 候选过滤/重排
        → 生成附来源的回答或结构化建议 → 输出
        → 保存步骤、错误、耗时和用量记录
```

随后按正式题面增加一个真实工具，让应用能完成必要的业务步骤。不要一开始就加入大量无关节点；每个节点应有明确输入、输出和失败处理。

该原型用于验证技术链路，不代表“文档问答”一定满足最终题意。

## 4. 建议的实现顺序

1. **确定输入与验收样例**：用少量真实资料，写清楚哪些问题应回答、哪些问题证据不足。
2. **搭建简单工作流**：先实现可靠的输入、检索和输出，保留中间结果。
3. **建立知识处理流程**：记录来源、版本和文档标识，明确切分方式及更新规则。
4. **比较检索策略**：观察向量检索、关键词能力、混合检索与 rerank 的实际效果。
5. **按需加入工具或 Agent**：只让它承担现有工作流难以预先确定的部分。
6. **验证部署与恢复**：从全新环境启动，检查持久化、配置缺失、依赖不可用和超时。

视频部署配置中列出了 seekdb 等向量存储选项。seekdb 是否必须使用、应承担什么数据职责以及支持哪些版本，仍需要正式题包确认；不能仅因配置示例出现它就补出强制要求。

## 5. 知识库部分值得投入的工作

切分、检索和生成需要分别观察。答案错误可能来自未检索到证据，也可能来自检索到证据后模型理解或使用错误，两者应分开修复。

建议保存“查询—候选片段—最终上下文—最终输出”的对应关系，并检查：

- 文档标题、章节和来源是否随片段保留。
- 精确术语、数字和编码能否检索到。
- 语义改写后的问题是否仍能找到相关证据。
- 多份文档冲突、旧版本资料是否会误导输出。
- 文档更新后索引与结果是否同步。

不要用扩大 top-k 或不断堆叠节点代替定位失败原因。重排和更长上下文也有耗时及调用成本，应通过固定样例比较。

## 6. 建议的验证与演示

以下为自测方案，不是官方评分规则。

| 验证点 | 可准备的证据 |
|---|---|
| 任务完成 | 固定问题集及预期结果，展示真实运行输出。 |
| 回答依据 | 输出能追溯到输入资料，证据不足时不编造结论。 |
| 检索质量 | 对比不同策略的命中与遗漏，保留候选记录。 |
| 工具可靠 | 检查参数、结果解析、失败、重试及副作用。 |
| 可观测性 | 能看到关键节点、错误位置、耗时和用量。 |
| 可复现性 | 新环境按说明导入流程、配置依赖并完成演示。 |

演示至少包含一条成功路径、一条证据不足路径，以及一次工具或服务失败。重点是表现系统如何处理真实运行状态，而非只展示预先挑选的理想回答。

## 7. 建议交付物与待确认事项

可提前准备可导入的流程配置、必要插件或工具源码、知识样例、环境与启动说明、验证记录和演示材料。敏感配置通过环境或配置机制注入，保持项目可被其他成员复现。

正式题面发布后，优先核对：必做业务、是否要求插件/内核开发、必须接入的数据库、允许的模型、运行环境、提交格式及评分方式。当前材料不足以承诺“只搭一个聊天界面即可参赛”。
