# 离谱辩题：运行说明

## 玩法

夜班辩论俱乐部只有一条规矩：你说一句，杠精主持人必须站到对面，并且翻出以前有人说过的胡话来压你。

玩家提交辩手、辩题、立场和一段辩词。应用先从旧档案里找能抬杠的记录，再给出主持人的反驳和离谱指数，最后把这一轮写回去。下一轮可以撞上刚才说的话。

六条预置辩题在 `data/seed_arguments.json`：猫应该交税、冰箱应该有投票权、周一应该被取消、梦想可以按斤出售、雨天必须配给免费热汤。样例输入在 `data/sample_input.json`。

## 分工

| 部分 | 做什么 |
| --- | --- |
| Dify DSL `docs/absurd_debate.dsl.yml` | 编排「输入 → HTTP 检索 → 回应 → HTTP 保存 → 输出」。回应是代码节点，不调用大模型。 |
| HTTP 服务 `src/server.py` | 只监听 `127.0.0.1:18604`。检索和保存都进 seekdb。 |
| seekdb collection `track04_debate` | 存在数据库 `track04_dify`。保存辩词，并用一次 `hybrid_search` 做全文加向量检索。融合用数据库里的 RRF，Python 不自己合并两路结果。 |
| 64 维向量 | `src/hashvec.py` 用标准库哈希把文本打成单位向量，不下载模型。 |

Dify Workflow 是用户入口；本目录的 curl 只用于验证 Dify 所依赖的 seekdb HTTP 工具服务。DSL 已在 Dify 1.18.0 自托管实例导入并发布，真实主链路证据在 `results/dify_run.json`。导入 DSL 并发布应用后，用 `src/run_dify_api.py` 调用 Dify `/v1/workflows/run`。`results/sample_run.json` 是后端工具服务 smoke test，不替代 Dify 运行记录。

## 环境

- 代码在 `/data/zouyuanwei/oceanbase/tracks/04_dify_workflows`。
- 已有 seekdb 监听 `127.0.0.1:2881`。不要重启它，不要 docker pull，不要改其他目录。
- 连接信息在本目录权限 600 的 `.env`。不要覆盖，说明里也不写密码。
- Python 3.11，项目已锁定 `pyseekdb==1.4.0.post1` 和 `PyMySQL==1.2.3`。本题没有新增依赖。
- DSL 按 Dify `1.18.0` 的 `0.5.0` 编写。原生同机运行时把环境变量 `DEBATE_API_BASE` 设为 `http://127.0.0.1:18604`；Dify Docker 运行时设为 `http://host.docker.internal:18604`，通过 SSH 隧道转发到 A6000 的 loopback 服务。
- 辩词里不要写英文双引号。检索节点的 JSON 模板会被双引号截断。保存节点用代码节点做了 `json.dumps`，不受这个限制。

## 启动

### Dify 主链路（已验证）

1. 启动 Dify 1.18.0 官方 Docker Compose，完成管理员初始化。
2. 启动本题 HTTP 服务，并建立 `0.0.0.0:18604 -> A6000:127.0.0.1:18604` SSH 隧道；不要暴露 seekdb 的 `2881` 端口。
3. 导入 `docs/absurd_debate.dsl.yml`，确认 `DEBATE_API_BASE=http://host.docker.internal:18604`，发布 Workflow，并在应用“访问入口 → 后端服务 API”创建临时 API Key。
4. 设置 `DIFY_API_BASE=http://127.0.0.1:8080` 和 `DIFY_API_KEY`，执行 `python src/run_dify_api.py`。预期看到 `DIFY_WORKFLOW_OK`，并生成 `results/dify_run.json`；API Key 不写入仓库。

本次验证结果为 Dify Workflow `succeeded`、5 个节点执行成功，输出包含 seekdb collection `track04_debate`、`refreshed: true` 和检索引用。

```sh
cd /data/zouyuanwei/oceanbase
. ./env.sh
uv run --locked python tracks/04_dify_workflows/src/server.py
```

启动时会把种子辩词 upsert 进 `track04_debate`，并 `refresh_index`。另开一个终端：

```sh
curl -sS http://127.0.0.1:18604/health
curl -sS http://127.0.0.1:18604/v1/motions
```

自测和样例一局：

```sh
cd /data/zouyuanwei/oceanbase
. ./env.sh
uv run --locked python tracks/04_dify_workflows/tests/test_debate.py
uv run --locked python tracks/04_dify_workflows/src/play_round.py
```

`play_round.py` 自己拉起服务，并用 curl 依次调用 `/v1/retrieve`、`/v1/respond`、`/v1/save`，再用同样的检索确认刚写入的辩词已经能被 hybrid_search 找到。成功后服务留在 `127.0.0.1:18604`。这一步不代表 Dify Workflow 已运行。

手工打一局时，先检索：

```sh
curl -sS http://127.0.0.1:18604/v1/retrieve \
  -H 'Content-Type: application/json' \
  --data-binary @tracks/04_dify_workflows/data/sample_input.json
```

样例文件的字段是 `argument`。检索接口接受 `text` 或 `argument`。把返回的 `hits` 和原输入交给 `/v1/respond`，再把回应交给 `/v1/save`。

## 样例里应该看到什么

夜班辩手以正方主张「猫应该交税」。检索应命中同题旧档案，而不是冰箱或周一。主持人站反方，回应里点出被引用档案的 id，并给出 1 到 99 的离谱指数。保存返回 `p_<round_id>` 和 `h_<round_id>`，且 `refreshed` 为 true。再用刚保存的辩词检索，结果里要有 `p_<round_id>`。

开放式抬杠没有唯一标准答案。同一输入必须得到同一句回应。

## 限制

- 主持人是规则，不是模型。同词会靠近，换一种说法不一定能检索到。
- 全文用 seekdb 的 IK 分词。检索词来自辩题里的内容词。
- 向量只有 64 维，只适合这个小游戏，不能当成通用语义嵌入。
- 重复发送同一辩词会 upsert 同一个 id，不会无限加行。

## 导入并运行 Dify Workflow

本 DSL 的回应节点是确定性 Python 代码，不调用模型服务，因此不需要 OpenAI 或 MiniMax 模型 Key；下面的 `DIFY_API_KEY` 只是调用 Dify Workflow API 时使用的应用 Key。

1. 在 Dify 1.12+ 控制台导入 `docs/absurd_debate.dsl.yml`。
2. 检查环境变量 `DEBATE_API_BASE`：原生同机使用 `http://127.0.0.1:18604`；Dify Docker 使用 `http://host.docker.internal:18604`。
3. 发布 Workflow 应用，在应用 API 页面复制 API Key。不要把 API Key 写入仓库。
4. 在能访问 Dify 的机器上执行：

```sh
cd /data/zouyuanwei/oceanbase/tracks/04_dify_workflows
export DIFY_API_BASE=http://127.0.0.1
export DIFY_API_KEY=app-REPLACE_WITH_DIFY_APP_KEY
python src/run_dify_api.py
```

成功标志是 `DIFY_WORKFLOW_OK ...`，并生成 `results/dify_run.json`。该文件只保存输入、Workflow 状态、运行 id 和输出，不保存 API Key。评审应同时看到 seekdb 服务日志中的 `/v1/retrieve` 和 `/v1/save`，以确认 Dify HTTP 节点实际调用了 seekdb 工具服务。
