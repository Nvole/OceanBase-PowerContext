# MiniMax：面向开发 Agent 的工程上下文工具

整理日期：2026-10-26  
材料：[课程 850](https://open.oceanbase.com/course/850) · [MiniMax 官方解析视频](https://www.oceanbase.com/video/9002481)

## 1. 这道题主要做什么

构建可复用的 SDD（规格驱动开发）工程上下文工具，接入现成开发 Agent，帮助它在持续变化的项目里理解当前要求、保留有效约束、定位相关代码与测试，并在任务切换后接着工作。

输入包括项目的需求、设计、代码、测试和本次开发任务。输出是对当前任务有用、来源可追溯、状态仍然有效的工程依据；Agent 使用这些依据修改代码并运行验证，结果再反馈给工具持续维护。

核心交付是上下文工具和效果证据。这里不必从头训练基础模型，也不应把工作停留在一次文档检索或通用聊天界面。

## 2. 视频明确的组件职责

| 组成 | 承担什么工作 | 演示时需要看见什么 |
|---|---|---|
| seekdb | 多源工程材料的存储、处理、管理和混合检索。 | 真实资料入库、检索条件、命中内容及来源。 |
| PowerContext | 记忆、上下文管理和任务接续。 | 决定、约束、进度等记录的读取和更新。 |
| 选手实现的工具 | 关联信息、判断有效性，按任务组织与持续维护。 | Agent 实际收到的上下文，以及它如何帮助完成开发任务。 |

指定组件应实际参与运行和演示。模型、Agent、组件版本及评分参数，课程明确要求以正式题包为准。功能可以组合实现，不要求为了展示架构而拆成多个独立服务。

## 3. Agent 需要拿到什么上下文

课程给出的重点可以整理为四组：

- **目标与有效约束**：本次改什么，哪些旧行为仍须保留。
- **设计和实现线索**：为什么采用现有方案，应该检查哪些接口、模块和代码。
- **验证方法与已有结果**：什么算完成，哪些测试要跑，哪些结果已经实际确认。
- **任务状态与接续信息**：已经做了什么、还缺什么、下一步是什么。

上下文需要指向来源与适用的工程状态。遇到过期、冲突或证据缺失时，可以明确指出问题，而不是把不确定信息包装成当前要求。

## 4. 建议的最小实现范围

本节是工程建议，不是官方指定测试项目。

选一个已有小项目，准备一次带约束的需求变更，例如增加一个字段或调整一个规则，同时要求旧接口保持兼容。先让 Agent 在单轮任务里使用上下文工具完成修改，再测试新需求和会话切换。

建议链路：

```text
项目资料与本次任务
  → seekdb 存储、检索相关材料
  → 关联需求、设计、代码与测试
  → 筛选当前有效的约束并标明来源
  → 交给现成开发 Agent
  → 修改与实际测试
  → 更新结果、决定和进度到任务记忆
  → 下一轮任务检索与接续
```

第一阶段只需要少量真实工程资料和一种 Agent 接入方式。先把一条更新链路做正确，再扩展更多文件类型和任务。

## 5. 建议的数据与状态设计

为了避免“旧资料检索到了就直接使用”，可为材料保存来源、版本/提交、更新时间、适用状态，以及它与需求、代码、测试的关系。

任务记忆可以区分已决定、已实现、待验证、验证通过和待处理问题。状态更新应有代码差异、测试结果或明确操作作为依据。

例如，上一轮记忆写着“功能已完成”，但代码实际只改了一半，或测试根本没跑，新会话不能照单全收。工具应帮助 Agent 核对真实项目状态后继续推进。

这类数据结构是实现建议，不是课程规定的数据库表结构。应优先使用正式组件已经提供的能力，避免额外建设与目标无关的通用平台。

## 6. 推荐的开发顺序

1. **固定基线项目与任务**：保存初始提交、需求、有效旧约束及验收测试。
2. **跑通真实资料入库和检索**：确保来源可定位，而不只是产生摘要。
3. **实现上下文组织**：针对当前任务选取材料，显式呈现有效性、冲突和缺口。
4. **接入 Agent 并完成一次修改**：记录它实际获得了什么，以及真实代码与测试结果。
5. **实现记忆更新**：将已验证结果、决定和剩余事项写回，避免把推测写成完成事实。
6. **验证需求变更和接续**：加入新规格或切换会话，检查旧约束、进度和代码状态是否仍对应。

## 7. 怎么证明工具有效

课程强调先看实际工程结果，再比较效率。建议至少覆盖三类任务：

| 任务类型 | 要验证的关键行为 |
|---|---|
| 首次修改 | 新需求实现，旧的有效行为和约束继续保留。 |
| 需求更新 | 被替换的要求不再误导 Agent，未变更约束仍然适用。 |
| 中断与接续 | 取回记忆后核对真实代码和测试，能够继续未完成任务。 |

可增加一组旧文档冲突案例，观察工具能否标出冲突与来源。无需要求工具预先知道所有项目细节。

对比实验应固定任务、模型、Agent 和运行条件，先检查关键验收是否通过，再比较耗时和调用用量。索引建立、资料更新和记忆维护的开销也应计入，不能只比较某一次回答长度或检索速度。

上述场景是将课程验证方向落实为自测的建议，不是官方评分权重。

## 8. 交付物与演示证据

课程明确的交付方向包括：可运行工具与接入说明、完整开发任务演示、可核对结果和技术方案解释。

建议把证据组织为一条连续记录：

1. 初始项目、任务和有效约束。
2. 检索到的资料、来源及 Agent 实际收到的上下文。
3. Agent 的修改、代码差异和测试结果。
4. 记忆中的状态更新及下一轮接续行为。
5. 相同条件下的对照结果与全部相关开销。

说明工具帮助 Agent 做对了什么，比单纯展示“有一个记忆面板”更有说服力。

## 9. 难点、待确认事项与视频索引

主要难点是新旧要求的有效性、工程材料之间的关联，以及记忆与真实状态的一致。向量检索只能找到相似材料，不能自动判定材料当前仍有效；长期记忆也不能替代验证。

正式题包需要核对指定 Agent/模型、组件版本、业务项目与测试任务、允许复用范围、运行限制和评分办法。

| 约略时间 | 内容 |
|---|---|
| 02:30–07:30 | 目标、工程约束与规格驱动开发。 |
| 07:30–11:45 | 信息随开发演进、上下文输出与接续。 |
| 12:45–14:30 | 指定组件职责与选手设计空间。 |
| 14:45–16:45 | 正确性、效率、证据及交付目标。 |
